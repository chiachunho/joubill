# Web groups, `/link`, invites, placeholder members and claiming

Moved out of `CLAUDE.md`, which keeps a short list of the rules that are easiest to break and links here. When the behaviour changes, update both.

**Groups created on the web have no chat** (`chat_type`/`chat_id` both NULL) and are joined by invite code. Everything that talks to Telegram must go through `telegramChatId(group)` (nullable) rather than `requireTelegramChatId` (throws), and skip quietly on null: `notify.ts` sends no group message (the audit row is still written), `DELETE /api/groups/[id]` and `delete-request` POST/DELETE send/edit/leave nothing, and the avatar/photo routes skip `getChat` (the UI draws initials). `requireTelegramChatId` belongs only to bot-side code that runs inside a Telegram chat. A pending deletion of a web group is approved in the app: `DeleteRequestBanner` on the group page shows 同意/拒絕 to every member except the requester (the requester's own request shows in the 刪除群組 row at the foot of 群組設定). It is shown for every group, not just web ones, because a member without Telegram can't see the buttons in the chat; it reads on mount and does not poll.

**A web group gets its chat later through `/link <邀請碼>`** (`src/bot/commands/link.ts`), typed in the Telegram group to bind. The decision is the pure `planLink` (`src/lib/link-plan.ts`): a wrong, revoked or expired code **and a sender who is not a member of that group** all get the same `INVITE_NOT_FOUND` text (a code only locates the group, it never admits anyone, and a reply must not say which codes exist); then a group that already has a chat is refused; then a chat already bound by an earlier `/link` (its group has a `chat_linked` audit row, so it is a real group even with no expenses) is refused with its own message; then a chat whose own `registerUser`-made row holds expenses is refused (two ledgers, manual merge, logged like `chatMigration`). Otherwise one transaction locks the web group `FOR UPDATE`, folds the chat's row in with `absorbGroup(…, { ex: tx, keepSurvivorCurrency: true })` (the row owns the `(chat_type, chat_id)` key, so it must go first; the web group's currency must win, the opposite of `chatMigration`'s case), then writes the pair via `telegramChatColumns`. It logs `chat_linked` (`recordType: 'group'`, payload `chatLinked` with the chat title). Pre-link records have no `notice_message_id` and are not re-sent; people already in the chat arrive through the usual membership tracking, never a batch add. **Unlinking** (issue #122) is `unlinkChat` + `leaveUnlinkedChat` in `src/lib/group-chat.ts`, called by `DELETE /api/groups/[id]/chat` (the Telegram 群組 page behind 群組設定's row of that name, `GroupTelegramPage` + `TelegramChatSettings`, shared by the Mini App and Web App) and by the bot's `/unlink` (`src/bot/commands/unlink.ts`), so the two can't drift. Any member may, and the group's origin doesn't matter: a Telegram-born group unlinks too, and its ledger stays in the App as a web group while the chat can start fresh. The decision is the pure `planUnlink` (`src/lib/unlink-plan.ts`: the one refusal is `no_chat`; membership is gated by the callers). One transaction locks the group `FOR UPDATE`, re-reads the chat under the lock (two simultaneous unlinks give one success and one `no_chat`, a 409), writes `noChatColumns()` (both columns NULL, never directly; it also resets 記帳通知發送位置, whose thread id belongs to the old chat) **and sets every record's `notice_message_id` to NULL**, since those ids belong to the old chat's messages and a re-link would otherwise try to edit them. Members, records and the invite code are untouched. It then logs `chat_unlinked` (payload `chatUnlinked`, the title as it was: the latest `chat_linked` title, else `groups.title`), and **after the response** the bot sends a farewell (the `/unlink` prompt is edited into it instead) and **leaves the chat** with `leaveChat`. Both are best effort, so a kicked bot or a deleted chat never undoes an unlink. The bot leaves on purpose: the chat's `registerUser`-made row would otherwise be recreated by the next message and the chat would drift into a second ledger nobody chose. Re-binding therefore means adding the bot back and typing `/link`. `/unlink` never acts on the command itself: it posts a prompt whose `unlink:yes:<groupId>` button is checked against `ctx.dbGroup` (a mistyped command in a chat must not detach a group). The prompt expires after `UNLINK_PROMPT_TTL_SECONDS` (10 minutes), because the bot leaves the chat and an unpressed prompt must not stay a loaded button; any callback also always answers, even when the database call throws. **`planLink` needs no change for re-linking**: `wasLinked` is read on the group that holds the chat, and an unlinked group no longer holds it; the next message in the old chat makes a fresh empty row, which `/link` absorbs unless it already holds expenses (`both_have_records`). Old cards go dead by themselves, since `guard()` checks an expense belongs to `ctx.dbGroup`. Push is no longer held back for the group (`telegramLinked` flips to false). Because the pair is an ordinary Telegram pair afterwards, `chatMigration` follows a later supergroup upgrade unchanged.

**Invites (`group_invites`, `src/lib/invite.ts` + `src/lib/invites.ts`)**: a group has at most one live code (`revoked_at IS NULL` and not expired), enforced by a partial unique index `group_invites_one_live_idx` and by `rotateInvite`, which locks the `groups` row (`FOR UPDATE`) before revoking the old code and inserting the new one in one transaction (a unique violation inside a transaction aborts it, so there is no retry; a code collision at 50 bits just throws). **Invites work for every group, Telegram ones included**: a member can have friends with no Telegram account, and the code is a member's deliberate act of sharing, unlike the content-derived guesses that `verifyInChat` guards against; resetting is how a member takes it back. Codes are Crockford base32, 10 characters (~50 bits), shown `K7M2Q-X9PAB`. The code length is the main defence against guessing, so don't shorten it; on top of it every lookup is **rate limited** (issue #121), see "Invite rate limits" below. Every unusable code (never issued, malformed, revoked, expired) returns the same 404 and text (`INVITE_NOT_FOUND`) so a response never says which codes exist, and the preview `GET /api/invites/[code]` requires login so it can't be used to enumerate. `invite.ts` builds the `/join/<code>` link and parses it back in one file (both ends of a contract); `POST /api/invites/[code]/accept` upserts `group_members` and flips `inactive` back to `active`, and logs `member_joined` only when the caller wasn't already an active member. `GET /api/groups/[id]/invite` is a pure read and answers `{ code: null }` for a group with none (everything created before invites existed): whoever presses 產生邀請碼 (`POST`) is the inviter on record, which a lazy mint on page view would get wrong. `POST` logs `invite_reset` only when it replaced a live code. `accept` decides in one statement (`INSERT … ON CONFLICT DO UPDATE … WHERE status <> 'active' RETURNING`) whether anything changed, so a double tap logs one `member_joined`. `INVITE_NOT_FOUND` lives in the DB-free `invite.ts` so the join page shows the server's exact words (as does `CLAIM_UNAVAILABLE`, what `accept` answers when the picked placeholder was merged or removed after the page loaded; nothing is joined then); only a 404 reads as invalid there, other failures offer a retry. `POST /api/groups` creates the group, the creator's membership and the first code in one transaction. Creating a group and entering a code (`groups/new`, `groups/join`, `join/[code]`) exist in **both** apps, and the code form continues under the app's own `basePath`, so a Mini App user never leaves Telegram's webview. The public share link is `/join/<code>`, outside `/app`, with its own `layout.tsx` that repeats the `/app` providers (a deliberate duplicate, like the other per-app layouts); a signed-out visitor goes through the store-wide 401 redirect to `/login?next=/join/<code>`. `GET`/`POST /api/groups/[id]/invite` also return `miniLink` (`joinLink` with the bot username from `src/lib/bot-username.ts`, null when unavailable) because the client has neither the bot username nor `TELEGRAM_MINI_APP_NAME`; the invite step offers both links. **Adding people has one entry, `AddMemberDialog`** (群組設定's member list 「＋ 新增成員」 and the one-person group card): it asks first, 新增沒有帳號的成員 (closes, then opens `AddPlaceholderDialog`; sequential, never nested) or 用邀請碼邀請 (stays in the dialog and renders `InviteActions`). There is no standing invite section. `InviteActions` renders its buttons only once the read says a code exists: loading is a skeleton, a failed read is an error with 重試, and `{ code: null }` is one line plus 產生邀請碼, so a copy or share button is never shown disabled or flashed then removed. Each kind of link is one row (`[複製] [分享]`, or 複製 alone across the row where `navigator.share` is missing); the row's title names the link so the buttons say only 複製 / 分享 and can't wrap, while their accessible names stay the full 複製網頁連結 / 分享 Telegram 連結. 重設邀請碼 is always offered and always confirms first. When the clipboard refuses a copy, the text is shown in a read-only, pre-selected field, because the links are not on screen anywhere else to select by hand. A Mini App user sent a web link can still paste it into 輸入邀請碼 (`parseInviteCode` accepts a link).

**Placeholder members (no account)**: `users.placeholder_group_id` (non-NULL) marks a member who has only a name. It reuses the `users` row so payers, splits, FX, notices and the audit log need no changes; the one column says both "no account" and "belongs to this group" (FK `ON DELETE CASCADE`, so the group's deletion takes them too). They have no `telegram_id`, `auth_identities` or `sessions`, and the Auth.js adapter's `getUserByEmail` / `getUserByAccount` filter them out explicitly. Created by `POST /api/groups/[id]/members/placeholder` (user + `group_members` in one transaction), renamed by `PATCH …/members/[userId]` (placeholders only; names unique per group, `src/lib/placeholder.ts`; the check-then-write runs under a per-group advisory lock, `src/lib/member-name-lock.ts`, since the name lives on `users` and no single index can enforce it), removed by the existing `DELETE` (409 when they have records, and the `users` row goes with the membership). `GET …/members` returns `isPlaceholder`. `chatMigration`'s `absorbGroup` repoints `placeholder_group_id` before deleting the absorbed group, or the cascade would erase them. **Deleting a group goes through `deleteGroup` (`src/lib/group-delete.ts`)**, never a bare `DELETE FROM groups`: the group cascades both to `expenses` and to its placeholder `users` rows, and the non-cascading `expense_payers.payer_id` / `expense_splits.debtor_id` foreign keys can be checked before the expense path has removed the legs, failing the whole delete for any group whose placeholder has records. It deletes the records first.

**Claiming a placeholder (merge into a real account)**: `mergeUserInto(tx, groupId, fromId, toId)` (`src/lib/member-merge-db.ts`) folds a placeholder into a real member inside the caller's transaction; the decisions are the pure, unit-tested `src/lib/member-merge.ts` (`validateMerge`, `planMerge`, `summariseMerge`). `from.placeholderGroupId` must equal the group and `to` must be a real account. **Payer rows sum into `to`'s row** (`UNIQUE(expense_id, payer_id)`); **split rows have no unique key, so skipping the combine would not error, just leave two rows for one person**. `amount` always sums exactly, so balances never move. `share_type` follows the edit form, which reads it from the _first_ row and treats the expense as uniform: two `equal` rows become `shares` weight 2 and the other `equal` rows weight 1; `shares`/`percent` add their `split_value`; `exact` stays; anything the merge can't keep honest (`adjustment`, whose deltas are relative to an equal split that just shrank) flattens the **whole** expense to `exact`. **The merge writes in bulk, and refreshes chat cards afterwards.** Payer and split changes are one statement per kind (`UPDATE … FROM (VALUES …)` for the per-row amounts), not one per row, so a placeholder with hundreds of records doesn't hold the group lock for hundreds of round trips. Each rewritten record's chat message still names the placeholder, so after the response (`after()` from `next/server`) `refreshClaimedNotices` (`src/lib/claim-notices.ts`) edits the newest `CLAIM_NOTICE_LIMIT` (20, Telegram's per-minute cap for a group) of them with `updateRecordNotice(…, { repost: false })`: edit-only, so a record that never had a message doesn't get a first one posted by a merge. Older cards keep the name they were posted with.

**Settlements between the two people** become "A → A" (`findSelfSettlements`): the merger chooses in the dialog (`selfSettlements: "keep" | "delete"`, default `keep`; the invite accept path always keeps). `mergeUserInto` only reports their ids (`selfSettlementIds`); the merge route deletes them afterwards through `logDeleted`, so each deletion is audited and tombstoned in the chat like any other. A kept one cannot pass the settlement PATCH's from ≠ to rule, so `SettlementForm` shows a note and disables 儲存 for it (`initial.from.userId === initial.to.userId`) — delete-only. The transaction takes `lockGroupMemberNames`, locks the touched expenses `FOR UPDATE`, repoints the non-cascading `created_by`/`actor_id` columns, and deletes the `users` row. Entry points: `POST /api/groups/[id]/members/[userId]/merge` (body `{ intoUserId }`; `GET …?intoUserId=` is the read-only preview for the confirm dialog, `MergeMemberDialog` in 群組設定; any member may merge, no consent, irreversible by decision) and the optional `placeholderUserId` on `POST /api/invites/[code]/accept` (the join-and-claim runs in one transaction, so a refused claim rolls the join back; `GET /api/invites/[code]` lists `placeholders` for the "你是下面其中一位嗎？" picker in `JoinPage`, empty once the viewer is a member). The bot's `/join` and membership tracking seat people without the picker, which is why the members-list entry exists. It logs `member_claimed` (`recordType:'group'`, payload `memberClaimed` with the affected `recordIds`) **after** commit. The bot needs no change: 誰分 reads `group_members`, and `profiles.ts` renders a null `telegramId` as plain text. `/add @handle` deliberately does not resolve them.

**One-person groups**: when the viewer is the only member, `GroupDetailPage` shows `SoloGroupCard` in place of the "all settled" banner (and the empty list says to add members first). The roster is read (`useGetMembersQuery`) only when `balance.balances` is empty — a lone member always nets zero, so no request is made for a group that visibly has other people. The roster is re-read on every mount (`refetchOnMountOrArgChange: true`) and neither the card nor the banner shows until it is current, so a cached roster from before someone joined can't put up a false card; inactive members count as members. The invite hint is `Platform.inviteHint` (shown wherever the invite step opens), a function of whether a Telegram link is on offer: the Mini App's advice is Telegram-specific (send the Telegram link, which stays in Telegram, or, when the server could not build one, the code for 輸入邀請碼), so it must not warn about leaving Telegram right under a link that doesn't. The card has no dismiss: it disappears when `Members` is invalidated by adding a placeholder, or on the next read after an invite is accepted. The card is only its text, one 新增成員 button and a link to 群組設定: the button opens the same `AddMemberDialog` as 群組設定's member list (see Invites above), so name errors and invite handling live in one place, and a missing code is still only issued by a tap on 產生邀請碼.

**Invite rate limits (`src/lib/rate-limits.ts` + `src/lib/rate-limit.ts`, `rate_limit_hits`)**: everything that resolves a code counts the attempt **before** the lookup, so a refused request never queries `group_invites`. `GET /api/invites/[code]` and `POST …/accept` share one bucket (`invite:user:<id>`, 30 per 10 minutes; a real join costs 2–4 hits) plus a looser per-IP one (`invite:ip:<hmac>`, 120, loose because an office, a carrier NAT and the CI runner each share one address); `enforceInviteRateLimit` runs right after `getAuth`, so a signed-out caller still gets 401 and spends nothing. Bot `/link` counts per sender (`link:tg:<telegramId>`, 10) and per chat (`link:chat:<chatId>`, 20); a bare `/link` (usage text) isn't counted. Windows are fixed, one row per `(key, window_start)`, incremented by a single `INSERT … ON CONFLICT DO UPDATE … RETURNING` for every key of the request; the pure `decide` refuses when any count is over its limit. Every attempt counts, valid code or not. The limiter **fails open** (logs and lets the request through): it is defence in depth, and a failing limiter would block every join. Rows older than a day are deleted by `sweepRateLimits` whenever a request opens a new window row (so at most once per key per window, in `after()` for the API), like expired merge tickets. `invite-rate-limit-coverage.test.ts` fails any file that calls `findActiveInvite` without counting the attempt first. The key has no foreign key; a merged account's counter just expires. IPs are never stored raw: the key is an HMAC keyed off the bot token with a purpose label, like `tg-photo-sign.ts`. **A refusal never says how long to wait**, since that would let a script time its next burst: the body is only `RATE_LIMITED.error` (嘗試太多次，請稍後再試), `Retry-After` is always the full window (600 s) rather than the time left, the join page shows no countdown (重試 stays enabled; an accept refused this way doesn't refetch the preview, which would spend another attempt), and the bot answers only the first refusal in a window (`firstRefusal`) and ignores the rest so it can't be used to flood the chat. The join page checks 429 before anything else and never shows `INVITE_NOT_FOUND` for it.
