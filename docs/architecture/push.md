# Home screen and push (`public/sw.js`, `src/lib/pwa.ts`, `src/lib/push*.ts`, issue #67)

Moved out of `CLAUDE.md`, which keeps a short list of the rules that are easiest to break and links here. When the behaviour changes, update both.

The Web App can be added to a phone's home screen and send push notifications. The Mini App does neither: Telegram's webview can't, and the chat already tells those users what changed, so every piece of UI here comes through a `Platform` slot that the Mini App fills with nothing (`DeviceSettings`, `GroupPrompt`, `GroupNotificationSetting`).

- **The interface says 加到主畫面, never 安裝 App.** People who dislike installing apps read "install" as an app-store download. The help page is `/help/add-to-home-screen`.
- **Manifest** (`public/site.webmanifest`): `start_url: "/app"`, `scope: "/"`. iOS ignores `start_url` and saves whatever page was on screen as the shortcut, so `LAUNCH_SCRIPT` (`src/lib/pwa.ts`, inlined first in the root layout's `<head>`, so it runs before React or any API request) replaces a fresh iOS launch on an `/app/…` page with `/app`, once per launch via a `sessionStorage` flag; nothing renders and no 401 can remember the old page. A notification tap's URL is marked `?via=push` by `recordPushUrl` (`openedFromPush`, built and read in `pwa.ts`), stays on its record, and the same script drops the marker from the address on any device. It is a string, not a function's source, because the bundler rewrites function bodies; `pwa.test.ts` runs that exact string against stubbed browser objects. Android honours `start_url` and opens site links in the installed app, so it is left alone. The scope is the whole site, not `/app`, because `/login`, the OAuth callbacks under `/api/auth` and the public `/join/<code>` must stay inside the home-screen app; out of scope, iOS opens them in an overlay and the session never reaches the app. On iOS the home-screen app does **not** share cookies with Safari, so people sign in once more there; the help page and the steps sheet say so.
- **`public/sw.js` is hand-written and push-only**: `push` and `notificationclick`, no fetch handler, no offline cache (a stale balance is worse than an error). No Serwist or other build plugin, so `next dev --turbopack` keeps working. It is served `no-cache` (`next.config.mjs`) and registered by `ServiceWorkerRegistrar`, which `AuthProvider` mounts in `mode="web"` only, so every Web App layout (`/app`, `/join/[code]`) gets it and the Mini App never does, without a one-sided edit to the paired layouts. Its payload shape `{ title, body, url, tag }` is built by `src/lib/push-notice.ts`.
- **What the device can do** is the pure `src/lib/pwa.ts`: `pushSupport` (`supported` / `needs-home-screen`, an iPhone in a Safari tab, which has no `PushManager` / `unsupported`) and `homeScreenOffer` (`installed` / `prompt`, Chrome handed over `beforeinstallprompt` / `ios-steps`, iOS gives a page no way to start it / `none`). `src/lib/install-prompt.ts` keeps the `beforeinstallprompt` event, listening from import time because Chrome fires it once and early. `AddToHomeScreenDialog` draws the iOS steps in iOS's own colours, not the design tokens; its step 1 names both Safari layouts (Share behind ⋯ in iOS 26's default 精簡 tab bar, in the toolbar with 底部 / 頂部 or before iOS 26), since a page can't read that setting.
- **Who is notified** is the pure `pushRecipients` (`src/lib/push-plan.ts`): created → everyone on the record; updated → everyone on it before or after, plus the creator; deleted → everyone who was on it, plus the creator; **never the actor**. `queueRecordPush` (`src/lib/push.ts`) then keeps current members with `push_muted = false` and at least one subscription. Group-level events (rate locks, joins, merges) are not pushed. The text is the pure `formatPushNotice`, written for its reader (你分 3,000 JPY), plain text, titled with the group name; a tap opens the record's edit page, a deleted record's `activity?record=`.
- **Delivery** runs in `after()` (falling back to fire-and-forget outside a request) and swallows every error, like `notify.ts`. A 404/410 from the push service deletes that subscription. The record id is both the Web Push `topic` and the notification `tag`, so three quick 誰分 taps leave one notification.
- **Optional**, like the extra login providers: `pushConfigured()` needs all three VAPID variables; without them nothing is sent, `GET /api/me/push-subscriptions` answers `configured: false` and the UI hides its sections. **A subscription endpoint must be on a known push service** (`isPushServiceUrl`, `src/lib/zod.ts`), because the server POSTs to whatever a client registers; a browser that brings a new push service needs a line there.
- **API**: `GET/POST/DELETE /api/me/push-subscriptions` (POST upserts on the unique `endpoint`, so a device that signs in as someone else takes the row over; the settings page re-POSTs whenever the browser still holds a subscription, which heals a server copy deleted after a 410; signing out (`WebAccountSection`) first deletes and unsubscribes this browser's subscription through `useForgetPushDevice`, so a signed-out device stops showing the account's records and the heal can't hand it to the next person without asking), `POST /api/me/push-subscriptions/test`, `GET/PATCH /api/groups/[id]/notifications` (the caller's `push_muted`, and whether the group has a Telegram chat).
- **Asking**: 個人設定 → 通知 (`NotificationSection`) is a per-device switch; `requestPermission()` is called first thing in the tap, before any `await`, because iOS refuses it outside a user gesture. The group page's card (`OnboardingPromptCard`) asks first for the home screen, then (in the home-screen app, or a desktop/Android tab once the shortcut was declined for good) for notifications, at most one card per visit, never in a group of one. The decision is the pure `nextPrompt` (`src/lib/onboarding-prompts.ts`); answers live in this device's `localStorage` (`src/lib/prompt-storage.ts`): 下次再說 waits `SNOOZE_DAYS` and gives up after `MAX_SNOOZES`, 不要再問, the system's 不允許 and turning the switch off in 個人設定 all stop it for good.
- **Can't be tested end-to-end in CI**: headless Chromium has no push service. The pure modules are unit-tested; `e2e/app-push.spec.ts` covers the manifest, the service worker's headers, subscription ownership and the group mute. Delivery needs a real phone.
