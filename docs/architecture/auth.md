# Web auth: linking, display names, avatars and account merging

Moved out of `CLAUDE.md`, which keeps a short list of the rules that are easiest to break and links here. When the behaviour changes, update both.

**Email auto-linking is on for GitHub and Google only, and deliberately off for LINE.** LINE's email is a separate permission the user may refuse and LINE does not promise it is verified, so matching on it would let anyone take over an account by registering its address. Telegram has no email at all, so a Telegram user who signs in with Google/LINE gets a **new, empty user** unless they link first. A person who already did that has two real accounts, which only an account merge (below) can join.

**Account linking (個人設定 → 登入方式, `LoginMethodsSection`)**: while signed in, `signIn(provider, { callbackUrl: "/app/settings" })` makes Auth.js bind the new account to the session's user (database sessions behave the same); if that identity already belongs to another user, the `signIn` callback turns it into a merge offer (see "Merging two accounts" below) instead of Auth.js's `OAuthAccountNotLinked`; every other failed OAuth callback lands on `/login?error=` (Auth.js sends `SignInError`s to `pages.signIn` and `AccessDenied` / `Configuration` to `pages.error`, both `/login`), where `authErrorRedirect` (`src/lib/identities.ts`) splits it: signed out, it stays and shows `loginErrorMessage`; signed in, it was a link that didn't complete (typically a cancelled consent), so it redirects to `/app/settings?linkError=<code>` and `LoginMethodsSection` shows `linkErrorMessage` above the list with a 再試一次, then drops the parameter (issue #105). The redirect doesn't say which provider failed, so `linkIdentity` remembers it in `sessionStorage` (`src/lib/linking-attempt.ts`, both ends). `OAuthAccountNotLinked` has no text of its own on purpose: signed in, the merge offer catches it first; signed out, Telegram and LINE send no email and GitHub / Google auto-link, so Auth.js never raises it. A new provider with a real email and no auto-linking would revive it. The same error redirect drops `?next=`, so a signed-out retry would land on `/app` instead of, say, the invite it started from: `src/auth.ts` names Auth.js's callback-url cookie (`CALLBACK_URL_COOKIE`, `src/lib/auth-redirect.ts`) and `/login` reads it back through `loginCallbackUrl`, only when `?error=` is present and keeping only the path. Two users are only ever merged by that explicit, confirmed flow. The action is `Platform.linkIdentity`: null in the Mini App, which only lists methods because OAuth can't run in Telegram's webview. Telegram is linkable from the web too (a Google-first account adding its Telegram): the adapter's `linkAccount` also sets `users.telegram_id`, which the bot and Mini App key on, inside the same transaction as the identity insert. It only succeeds when no other account owns that Telegram id; otherwise it becomes a merge offer, like any other identity that belongs to someone else. Telegram can't be unlinked. Avatars are covered in "Display name and avatar" below; the `<img>`s set `referrerPolicy="no-referrer"` so provider-hosted pictures load. `GET /api/me/identities` and `DELETE /api/me/identities/[provider]` back the section; the DELETE is scoped to the caller and 409s on the last method (`canUnlink`, `src/lib/identities.ts`). The adapter's own `unlinkAccount` has no such guard, so never call it for this.

**Display name and avatar (issue #101, `src/lib/profile.ts` + `src/lib/avatars.ts`)**: two layers on `users`, on purpose. `first_name` / `last_name` are the **provider's** name and `upsertTelegramUser` overwrites them on every bot update and Mini App open; `display_name` is the person's **own choice** and only `PATCH /api/me/profile` writes it (trimmed, whitespace collapsed, at most `DISPLAY_NAME_MAX` = 32 user-perceived characters, no control, bidi or zero-width characters (ZWJ allowed, for emoji), `""`/null resets: `normaliseDisplayName`). Writing a chosen name into `first_name` would be undone the next time they open the Mini App. **Every rendered name goes through `displayName()`**, usually via `labelUser` / `labelMember`, whose `Profile` makes `displayName` a _required_ key so a query that forgets to select it fails to compile; `USER_COLUMNS` carries it for the bot; and `display-name-coverage.test.ts` fails any file that selects `users.firstName` without `users.displayName` (for rows that go straight into a JSON response, which the compiler can't see). `NoticePerson` snapshots capture it too, so the audit log keeps the name as it was; snapshots written before the column have no key, which `displayName()` reads as unset. Names are not unique: nothing blocks two members choosing the same one, and `memberLabels` (used by `MemberSelect` and `ExpenseForm`'s payer and participant rows) appends the provider name, or `#n` when that collides too, to colliding labels; placeholder names are checked against members' display names (`isDuplicateName`). Pictures: each login keeps its own `auth_identities.name` / `picture_url`, refreshed by Auth.js `events.signIn` (`syncIdentityProfile`, `src/lib/auth/identity-profile.ts`; it reads the provider's raw claims through `identityProfile`, since `linkAccount` never sees the profile) and by `upsertTelegramUser` for the Telegram row; the same call fills `users.avatar_url` only when it is empty. `upsertTelegramUser` writes `avatar_url` only when Telegram sent a photo (it used to write NULL and erase a Google picture). `users.avatar_source` (null = automatic) picks one; `pickAvatar` resolves it: the chosen login while it is linked and has a picture, else Telegram's photo (the live one through the bot API; when the bot can't fetch it, the `picture_url` Telegram last supplied through initData or a Telegram sign-in), else the other logins in `LOGIN_PROVIDERS` order, else `users.avatar_url` (covers people who haven't signed in since the column existed). `/api/me/profile` and `/api/groups/[id]/avatars` both go through `resolveAvatars`, which caches only the Telegram lookup per Telegram id (`TtlCache`, bounded, so a long-lived instance doesn't keep every id it ever saw); the choice is made fresh each request so a change shows at once. `PATCH /api/me/profile` loads the pictures once (`loadAvatarInputs`) and reuses them to validate the source and build the response. Unlinking the login the avatar came from resets `avatar_source` in the same transaction. The UI is the profile card in `PersonalSettings`: a pencil beside the name (`DisplayNameDialog`) and, only when there are two or more pictures to choose from, the avatar itself as a button (`AvatarSourceDialog`); no OAuth is involved, so both apps have it. `updateProfile` invalidates every people-bearing tag type (`peopleTags` in `src/store/api.ts`), since the viewer's name appears in all their groups. Chat messages already posted keep the name they were sent with.

**Merging two accounts (`src/lib/account-merge.ts` + `account-merge-db.ts`, issue #99)**: the proof that one person owns both accounts is being signed in as A and then completing an OAuth sign-in that belongs to B, nothing less. The Auth.js `signIn` callback (`mergeRedirect`, `src/lib/auth/merge-ticket.ts`) sees the session cookie and an identity owned by another real user (an `auth_identities` row, or for Telegram also `users.telegram_id`), writes an `account_merge_tickets` row (10 minutes, single-use) and returns `/app/settings/merge`, so no session is created for B. The ticket id travels **only** in the httpOnly `merge_ticket` cookie scoped to `Path=/api/me/merge`, never in a URL. `GET /api/me/merge` is the preview, `POST` (`{ keepUserId, selfSettlements }`) claims the ticket with `UPDATE … WHERE consumed_at IS NULL RETURNING` in the same transaction as `mergeAccounts`, `DELETE` cancels; every missing, expired, used or someone else's ticket is the same 404 (`MERGE_TICKET_NOT_FOUND`). The page (`AccountMergePage`) is a pair like any other, but the merge itself is web-only because OAuth can't run in Telegram's webview: with `Platform.openInBrowser` set (the Mini App, entered from 登入方式 → 合併另一個帳號) it reads no ticket and only explains the steps, with a button that opens `/app/settings` in the browser. The web copy reloads with `location.replace` after a merge, because the current session may now belong to the other user (and so Back can't return to a page whose ticket is gone); a 404 sends it back to 個人設定 with `?merge=expired`. The pure part refuses two different Telegram ids (`telegram_id` is unique) and two different uids of one provider (the settings page assumes one per provider), suggests keeping the Telegram holder, then the busier account, then the older one (`suggestKeep`), and plans memberships (one row, active if either was) and beancount configs (the kept account's wins). `mergeAccounts` locks both `users` rows in id order, runs `planMerge` + `applyMergePlan` (shared with claiming a placeholder) once per group the absorbed account has records or membership in, then moves **every** column pointing at `users.id`, the cascading ones (`auth_identities`, `sessions`, `push_subscriptions`, `group_delete_requests`, `user_beancount_configs`, `group_members`) before the delete; it clears the absorbed `telegram_id` before the kept row takes it, fills only the kept account's empty profile columns (`mergedProfileFields`, `display_name` and `avatar_source` included), and deletes the absorbed user. A new `users.id` reference must be added there too; a non-cascading one goes in `repointUserReferences` (`member-merge-db.ts`), which claiming a placeholder shares. After commit the route logs `account_merged` once per group (`recordType: 'group'`, payload `accountMerged` with the rewritten `recordIds`, matched by `loadRecordHistory` like `member_claimed`), deletes "A → A" settlements when asked, and refreshes the newest chat cards with `refreshClaimedNotices`.

**In-app browsers**: Google answers `403 disallowed_useragent` inside LINE's / Telegram's built-in browser, so `/login` disables the Google button there (`isInAppBrowser`, `src/lib/in-app-browser.ts`) and `inviteLink` appends `?openExternalBrowser=1` so LINE opens shared links externally. LINE's button is listed first (it signs in without a prompt inside LINE).
